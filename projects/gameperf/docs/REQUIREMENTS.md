# GamePerf Studio｜需求与产品蓝图 v0.3

## 1. 产品定位

不是一次性汇报页，也不是已经具备自主执行能力的 Agent 大屏。它是游戏性能域的长期维护入口：**全局能力地图 + 业务记录工作台 + 可验证方法改进的证据层**。

面向你的真实起点：游戏性能优化小组负责多设备游戏调优，已经有基于高通调度框架进行参数自动寻优的 Agent。保留这个执行系统，用薄适配连接新的工作台，避免为画蓝图而重写已有成果。

核心目标：将“完成某次参数优化”逐步升级为“覆盖完整业务，并能积累和验证更有效研发方法的体系”。整体目标不能用 Agent 数量、运行时长或代码修改量代替。

## 2. 四个需求方向

| 方向 | 你的诉求 | 网站承载方式 | 验收对象 |
|---|---|---|---|
| 横向业务闭环 | 适配、调优、送测、媒体和用户反馈连通 | 架构图、任务、实验、反馈、版本记录 | 一个问题是否形成可复现的结论 |
| 纵向能力深入 | 每个步骤可继续拆到策略、分析和获授权代码 | 父子节点、下钻视图、职责契约、关联任务 | 能力是否有明确输入输出、权限和停止条件 |
| Agent 方法改进 | 让诊断、搜索、工具、流程持续变强 | 独立候选页、旧版/新版、留出任务、可比预算和审核 | 新方法是否在独立任务上优于旧方法 |
| 向上组合、横向复用 | 你的体系是领导网络的一部分，共享公共能力 | 上层目标接口、域编排、共享能力目录、回传契约 | 上下游是否能稳定交换目标、证据与结果 |

产品代码改好，不等于 Agent 自身变强。两类改进可以并行，但必须分别记录和验证。

## 3. 信息架构与当前实现

| 页面 | 当前可做的事 | 尚未实现的业务能力 |
|---|---|---|
| 全局蓝图 | 动态链路示意、选中契约、筛选、子能力下钻、维护目标、关联新任务、汇报模式 | 实时运行拓扑、自动服务发现 |
| 需求与边界 | 四方向、产品目标、实现与规划边界；目标可编辑 | 任意网页文案所见即所得编辑 |
| 业务任务 | 新建、编辑、分阶段与状态管理、关联实验 | 自动调参、任务派发、流水线执行 |
| 实验与证据 | 假设、对照、环境、指标、原始证据引用、提交冻结 | 真机采集、自动性能判定、证据链接自动抓取 |
| 能力进化 | 方法候选、版本、留出任务、预算与人工独立审核记录 | 自动修改自身、自动晋升、底座模型训练 |
| 反馈闭环 | 记录媒体/用户反馈，一次性转为待办任务 | 爬取媒体、收集用户个人数据、自动归因 |
| 能力目录 | 新增节点、修改父子关系、职责和负责人；禁止父子循环 | 任意边自由连线编辑、自动生成运行实例 |
| 业务接入 | 已有 Agent 回传任务与实验草稿的 REST 接口、幂等事件 | 任意命令执行、SSH、设备代理、模型调用 |
| 演进路线 | G0、并行 G1-A/G1-B、G2 的目标与验收条件 | 自动计算团队项目进度 |
| 部署与维护 | 运行模式、账号角色、导入导出、操作记录 | 企业 SSO、多租户项目隔离、不可篡改审计 |

全局图保留稳定的核心业务结构。新增根节点通过“新增架构节点”呈现；子节点在下钻与能力目录中显示。结构维护依赖父子关系，而不是任意连接所有节点。每个节点可下钻，没有子节点时允许继续拆分；不把层数当作进化程度。

## 4. 视觉与交互原则

深空蓝底色、青绿业务链路、紫色方法改进、暖色验收边界。装饰动效采用 CSS/SVG，网页不依赖外部图片、字体、分析脚本或 CDN。

动效表达信息关系，不制造实时遥测。七步“链路演示”由用户主动启动，会自动结束，可随时停止；演示不创建、修改、执行或审核业务记录。页面隐藏时停止演示并暂停装饰动效。提供动效开关，并尊重系统减少动态效果设置。

节点点击更新右侧契约；点击“下钻”进入子能力；编辑通过统一表单完成。汇报模式隐藏侧栏与非关键控件，Esc 退出。手机导航可折叠，全局图在自己的容器内横向滑动，契约在图下方；表格和看板内部滚动，不撑破页面。

事实、人工维护状态、示例数据与装饰动效必须明确区分。系统没有连接到设备时，不显示设备在线数、GPU 负载、性能提升或“正在优化”等伪实时指标。

## 5. 数据与业务边界

沿用 schemaVersion=1：project、nodes、tasks、experiments、evolutions、feedback、audit。服务端保持角色、CSRF、版本冲突、提交冻结与参与者不能自审的限制。

本机版保持旧版 `gameperf-studio-v02` 存储键以兼容已有数据结构，但不同 file URL、浏览器或设备的本地存储可能不同。升级前先导出旧版 JSON；在新版“部署与维护”导入。数据不会自动上传。

服务器首次启动只有蓝图，没有示例任务。浏览器与后端同源，业务数据需登录；离线或后端失败不能悄悄回落到另一份本机数据。JSON 导出不是账号、令牌及数据库的完整备份。

公司批准前，个人海外服务器仅放蓝图、脱敏示例及被批准的记录。不要上传内部源码、完整 Trace、用户隐私日志、供应商配置、账号或凭证。

## 6. 业务接入顺序

第一步：网站私有部署，确认目标、第一条代表性任务、评测责任人和允许数据范围。

第二步：现有调参 Agent 使用写入型令牌上报脱敏任务，再关联实验草稿。接口接收成功，仅表示记录到达。

第三步：接入获准的实验执行器、设备队列与原始证据存储，使用明确工具边界，不通过网页任意 shell 实现。

第四步：围绕一个局部模块探索代码候选，同时围绕诊断或搜索效率探索方法候选。分别用真实实验与独立任务评价。

第五步：接入送测、反馈和上层组织目标接口，优先复用经过验证的公共工具。

## 7. 当前发布门槛

本版：网页静态与交互测试通过，既有接口回归通过；具体结果见 QA.md。不将这些检查等同服务器上线验收。

上线前：目标机 Docker/Compose、已有站点、Caddy 管理方式与端口只读核对；建立独立目录；本机端口初验；真实登录、刷新/重启持久化、备份恢复与角色权限复验；明确域名和访问范围后才增加 HTTPS 入口。

新增执行能力前：完成现有系统映射、数据使用批准、设备恢复演练和独立评测设计。
