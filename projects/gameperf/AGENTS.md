# GamePerf Studio: engineering instructions

## Read before changing
- docs/STATUS.md, README.md, docs/ARCHITECTURE.md, docs/API.md.
- app/models.py is the input-contract source of truth; app/seed.json is a NEW-database seed, not the live database.
- docs/blueprint-v0.1.md is a design proposal, not authorization to touch hardware or vendor source.

## Preserve
- Keep the existing tuning Agent external; prefer a thin adapter.
- Never claim that record ingestion or a UI status means a device executed, a benchmark improved, or an Agent evolved.
- Product experiments and Agent-method candidates remain separate, with independent evidence.
- Authorization, contributor/self-review restrictions, CSRF, version checks and immutable submitted candidates stay server-enforced.
- No remote command execution, eval, shell-from-request, provider keys in JS, embedded server credentials, or public anonymous business data.
- Never overwrite existing server websites or open public ports without explicit authorization.
- No default login accounts or fixed deployment passwords. Tests create isolated temporary accounts only.
- Local demo must remain clearly labeled; do not silently fall back to local data if the server fails.

## Work flow
- Scope small changes. Do not add a large Agent framework, queue or front-end toolchain without demonstrated need.
- Extend typed input models and tests before changing API contracts.
- Escape user strings in UI rendering. Never insert imported text as trusted HTML.
- Every DB mutation remains transactional and every edit requires an expected version.
- Schema changes require a migration, backup, rollback/forward plan and regression tests.
- Run `python -m pytest tests -q`, `node --check web/app.js`, and regenerate the portable file using `python scripts/build_demo.py` after UI changes.
- Do not rewrite the original user blueprint solely to match a software implementation shortcut.
- Update docs/QA.md honestly: list tested behavior separately from untested infrastructure.

## Deploy boundaries
- Read docs/DEPLOYMENT.md; use a dedicated directory and subdomain.
- First inspect OS, architecture, occupied ports, proxy, Docker, data authorization and available secure execution route.
- Do not request passwords/private keys in chat. Do not include .env, DBs, backups or tokens in archives/images.
- Actual server operations, DNS, HTTPS and backup/restore must be verified before claiming deployment success.

## v0.3 continuation
- Read docs/REQUIREMENTS.md before changing the product intent. The UI is a control/record plane, not real-time scheduling.
- Read docs/SRV47_DEPLOYMENT.md before any server work. Reuse existing srv47/serverctl; never restart proxies or fall back through other SSH routes without explicit approval.
- Graph selection, drill-down, filters and presentations MUST NOT mutate business state. A labeled tour is illustrative only.
- Keep prefers-reduced-motion and explicit motion-off controls. Never invent live telemetry to make the UI look active.
- Preserve the v02 localStorage key unless a tested migration is included. Different file URLs may still require export/import.
- Default seed has no server business records. QA screenshot data is illustrative; never promote it to runtime evidence.
